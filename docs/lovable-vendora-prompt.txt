Build a polished, responsive operations ERP for Vendora, a snack vending machine business in Indonesia. This is the operator back office, separate from the customer-facing Flutter kiosk. Make it feel like a focused operations product that helps staff find machines needing attention, refill snacks, and investigate payment or dispensing issues.

DESIGN DIRECTION
Use the supplied Vendora logo and preserve its proportions. Navy #0F2A3D and teal #12A497 are the brand colors; use darker teal #087F75 for readable text and action buttons on white. Use a light #F8F9FA workspace, white surfaces, restrained borders, 12–16px radii, and subtle shadows. Prefer clear hierarchy and useful density over large decorative cards. Use a readable sans serif such as Plus Jakarta Sans or Inter, 14–16px body text, 24–28px page titles, and an 8px spacing rhythm. Reserve amber and red for actionable warnings, green for confirmed successful states. Every status needs a text label as well as color. No gradients or oversized marketing sections.

USERS AND PRIMARY TASKS
An operator checks exceptions and sales; a refill worker finds a machine and updates stock; an administrator manages products, machines, and kiosk advertisements. These are task scenarios, not implemented permission roles. Do not invent a role-switching UI or claim permissions exist.

APP STRUCTURE
Create a consistent shell with a 240–256px desktop sidebar, current-page highlight, breadcrumbs on detail/edit pages, page title, short description, and one primary action. Navigation: Overview; Machines; Products & stock; Transactions; Advertisements. Show the authenticated user's email and Sign out consistently. On phones use an accessible menu drawer or expandable menu; every destination and Sign out must remain reachable. Support 375px, 768px, and 1440px layouts. Tables may scroll horizontally within their own container, never overflow the whole page. Use cards for suitable mobile lists. Persist filters in the URL, reset pagination when filters change, and show result counts and clear-filter controls.

1. OVERVIEW
Show total machines, confirmed items sold today, settled revenue today in full IDR, and low-stock slot count. Use a clearly labeled date/time context. A trend is shown only when comparison data exists; never invent percentage growth. Put an actionable attention queue near the top: refund required, needs review, low stock, and missing or stale machine contact. Each item links to the relevant filtered screen. Show recent transactions and a short machine list with View all links. Include useful zero-data states and onboarding actions: Add machine, Add snack product, Assign product to slot. Do not add a fake analytics chart just to fill space.

2. MACHINES
Search by location or UUID. Separate configured operational status (active, maintenance, inactive) from connectivity; active does not mean online. Connectivity should use last_heartbeat_at with an explicitly configurable freshness threshold and show Unknown when no heartbeat has been received. Display location, short ID with copy/full ID access, configured status, last contact, slot count, and actions. Label any new connectivity derivation as a proposed frontend rule until agreed with the backend.
The detail page shows location and breadcrumbs, status, last heartbeat, product/slot cards, stock counts, and Add slot. Keep API tokens behind a deliberate reveal with copy feedback. Never show a green connected claim based only on configuration. Each slot shows slot number, snack image/name, price, current_stock/max_capacity, a bounded fill bar, hardware status, and Refill/Edit. Distinguish disabled from jammed/error. Use plain language instead of node, spiral integrity, hardware core, or provision.

3. PRODUCTS & STOCK
Separate global snack catalog information from machine-specific stock. List image, name, IDR price, aggregated stock, and machine assignments. Make per-location counts available by click/tap and keyboard, not hover-only tooltips. Link stock locations to their machine. Add/Edit product includes name, positive price, optional description, optional image, image preview, upload feedback, inline validation, and Save/Cancel. Preserve entered values after failure. A slot currently requires a product in the database: do not offer an unassigned-slot option without explicitly proposing a schema change. Refill/Edit slot shows product selector, current quantity, capacity, and operational/error/disabled status. Validate quantities and prevent values above capacity in the proposed UI; call out any additional backend validation required.

4. TRANSACTIONS
Create a readable ledger with search by full/partial transaction UUID, location, or product; status filter; result count; Previous/Next pages; and filter-aware CSV download. Add date range and machine filters only as clearly identified API extensions. The existing CSV export covers the displayed page, so label it Export this page (CSV) unless implementing a separate full export. Show date/time, short ID, location, product, exact IDR amount, readable status badge, and an expandable details panel with full UUID, payment method, and available reference/failure data. Never place a nonfunctional Receipt button in the UI.
Preserve these actual states: pending, paid, dispensing, settled, failed, expired, cancelled, refund_required, needs_review, refunded. Only settled contributes revenue and confirmed delivered-item totals. Payment and product delivery are distinct. For refund_required and needs_review, an operator may mark the transaction refunded after completing the refund externally. Only needs_review may be marked dispensed/settled after physically verifying delivery. Use an explicit confirmation showing transaction ID, amount, location, and the action's meaning. Mark refunded records an external refund; it does not call a payment-provider refund API. Do not invent automatic refunds or modify kiosk payment state transitions.

5. ADVERTISEMENTS
Show image/video previews with live, scheduled, paused, and ended states, title, duration, placements, schedule, target machines, Edit, and Delete. Support PNG/JPG/WebP/MP4, max 50MB. Placements are sidebar, attract, and dispensing. Payment screens never show ads. Images show for 3–60 seconds; video plays to completion without sound. Explain that no machine selection means all machines. Show the schedule timezone, preserve form state on validation failure, and confirm deletion with the advertisement title. A paused advertisement stays available for later reuse.

FEEDBACK, ACCESSIBILITY, AND STATES
Use nonblocking, dismissible success notices with a polite live region. Show every failure visibly, with actionable messages near the affected field and an error summary when needed. Do not hide errors or force a Continue modal after routine saves/sign-in. Destructive or financial-resolution actions require confirmation. Dialogs have accessible names, Escape/Close, focus trapping, focus restoration, and scrollable content on small screens. Use semantic forms and tables, associated labels, visible keyboard focus, minimum 44px touch targets, good contrast, and reduced-motion support. Implement loading, empty, filtered-empty, validation-error, upload-error, request-failure, and success states. Retrying a failed request must not discard entered values. Do not claim data is real-time unless an update mechanism exists; otherwise show last refreshed and a refresh action.

TECHNICAL AND HANDOFF CONSTRAINTS
The existing application is Ruby on Rails 8.1, server-rendered ERB, Tailwind CSS 4, Stimulus, Turbo, Devise sessions, PostgreSQL, and Active Storage. Existing operator routes: /, /machines, /machines/:id, /inventories, /transactions, /transactions/:id/resolve, /slots, /advertisements, and /users/sign_in. Preserve route meanings, model fields, authentication, CSRF handling, and payment rules. Kiosk bearer-token endpoints under /api/v1/kiosk are separate; never expose kiosk tokens in a browser client.
If generating a React/TypeScript prototype in Lovable, use reusable components, local deterministic fixtures, and a typed adapter boundary for future Rails integration. Do not replace Rails with Supabase, invent JSON endpoints that already work, connect real payments, store production tokens, or claim the prototype is integrated. Document API additions separately. Suggested new filters, attention queues, automatic refresh, and connectivity calculations must be marked as proposed capabilities until implemented. Keep actual timestamps in ISO format and format IDR with Indonesian separators; use an explicitly configured display timezone such as Asia/Jakarta rather than assuming the server's timezone.

DELIVERABLES AND ACCEPTANCE
Create connected, interactive screens for all five sections, machine detail, product create/edit, slot refill/edit, advertisement create/edit, transaction details/resolution, and sign-in. Include realistic snack fixtures such as potato chips, crackers, biscuits, and nuts. All visible controls must perform an action or clearly explain why they are unavailable. Provide a small component/token inventory and integration notes explaining which behaviors are prototype-only. Check desktop and mobile overflow, keyboard navigation, success/error feedback, persistent filters, and confirmations. Prioritize Overview, Machines/detail, and Transactions first, then Products & stock and Advertisements, while keeping the shell consistent throughout.
